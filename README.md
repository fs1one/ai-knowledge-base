# AI Knowledge Base

个人文档知识库：上传文档 → 切分 → 向量化 → 检索 → 带引用回答。

## 技术栈
- Java 17 / Spring Boot 4.1.1 / MyBatis-Plus 3.5.17
- MySQL 8（向量先存 JSON，v1 用内存余弦相似度）
- LLM：手写 HTTP 调国产 API（不引 Spring AI）

## 计划功能
- [x] 文档上传与解析（**目前只支持 TXT**，PDF / MD 待接）
- [x] 两种切分策略对比（定长 vs 段落感知，见下节）
- [ ] Top-K 检索 + 带引用回答
- [ ] 30 条评测集 + 召回率基线

## 切分策略对比（实测）

同一份文档 `http/big.txt`（4820 字节，归一化后 **1844 字符 / 10 段**，段间是单换行、零空行），
分别用两套策略切分。两套结果在库里**并存**（`chunk` 表按 `(doc_id, strategy)` 隔离，不互相覆盖）。

统计口径：`TRIM(content)` 后判断块尾字符是否属于 `。！？.!?；;…`。

| 策略 | 块数 | 最短 | 最长 | 平均 | 总字符 | 句末结束占比 |
|---|---|---|---|---|---|---|
| `fixed`（size 800 / overlap 100） | 3 | 444 | 800 | 681 | 2044 | 66.7% |
| `paragraph` | 3 | 345 | 782 | 616 | 1849 | **100%** |

### 结论

- **块数一样（都是 3），差别在边界质量**：定长有 1 块结尾停在非句末位置，段落感知 3 块全部落在句号上
- **定长多出 200 个字符**：`2044 − 1844 = 200`，正好是 2 次重叠 × 100。段落感知总字符 1849 比原文多 5，
  是合并时把段间单换行升级成 `\n\n`（+7）扣掉块边界丢弃的分隔符（−2）
- **代价是块长更不均衡**：段落感知极差 437（345→782），定长只有 356（444→800）。
  embedding 时要按最长块预留上下文，不能按平均值估
- **段落感知不加 overlap**：段落边界本身就是语义边界，再重叠会让相邻块内容重复，召回时同一段被引用两次。
  overlap 是「下刀位置与语义无关」时的补丁，这里不需要
- **超长段落（> size）内部回退到定长并保留 overlap**：那一段内部没有语义边界可用，和定长面临同一个问题

### 口径说明

如果按「Java 里直接看块尾最后一个字符」统计，`fixed` 会是 33.3% —— 因为中间那块结尾带着换行 `\n`。
本表用 `TRIM` 后的口径（**块尾换行不算内容**），两者差一块，不是数据错了。

### 已知局限

样本只有 1844 字符、10 段，两套策略都只切出 3 块，**统计意义有限**。
真正拉开差距要等接入 PDF / Markdown（有标题层级、列表、代码块）之后重测。
